# Plan: dialog close button (0.7.1); job history and System → Schedules (0.8.0)

Round 4, 2026-10-20 (Codex rounds 1 and 3 applied; closure runs reworked after RDockPanel's answer: all 9 of its schedules are closures). Requested by RDockPanel (Core
0.7.0, 9 schedules, job kinds `deploy.run`, `deploy.publish`, `backup.run`,
`docker.image_pull`). **Plan only; not approved yet.**

## Releases
- **0.7.1, part A:** the dialog close button. SPA only, kit compatible, no
  migration.
- **0.8.0, parts B and C:**
  - job history, descriptions, details and auto refresh on the Queue page;
  - the Schedules page with run history, task summaries and Run now.
  - They ship together: a schedule's outcome is written by its job's terminal
    transition. Both need migrations, new admin routes and permissions, and a
    `Job` method with a default.

## Part A (0.7.1): a close button on every dialog

**Today:**
- `components/ui/dialog.tsx` renders an `h2` and its children. The only ways
  out are Escape and the dialog's own buttons.
- The same component is the SDK kit's `Dialog` (`lib/host.ts`).
- Native `showModal()` focuses the first focusable descendant. A non-native
  fallback sets `open`.

### Design
- **The button:** an icon `×` button in the header's top right corner,
  `aria-label={t("action.close")}` ("Close" / "Đóng"), calling `onClose`.
- **Focus:** the button comes after the children in the DOM, placed with
  `absolute right-3 top-3` in a `relative` container. Focus on open therefore
  stays on the first field. The title gets `pr-8`.
- **Labelling:** the dialog is labelled by its `h2` (`aria-labelledby` with a
  `useId`), instead of `aria-label={title}`. This allows `title: ReactNode`,
  which the SDK's `ui.d.ts` already declares.
- **`closeButton?: boolean`** (default `true`). The shell's mobile drawer
  passes `false`, since it has its own X.
- **`closeDisabled?: boolean`** disables the × button **and** Escape. Busy
  dialogs pass it: `SchemaFormDialog` while submitting, confirm dialogs while
  their write runs. They do not guard closing today.
- **Kit:** extensions get the button without rebuilding, because the host
  renders it. `ui.d.ts` gains the two optional props; `ui` stays 2.

### Test A
- **Vitest:**
  - × closes the dialog;
  - `closeButton={false}` renders no button;
  - `closeDisabled` disables × and Escape;
  - the accessible name is the title;
  - the existing dialog tests keep passing, with locators that relied on
    `aria-label` checked.
- **E2E (Chrome, native `<dialog>`):**
  - focus lands on the first field when the dialog opens;
  - Escape closes it, and is blocked while `closeDisabled`;
  - focus returns to the opener;
  - a long dialog scrolls with × reachable;
  - × closes a confirm dialog;
  - no CSP violation.

### Docs A
- Guide `admin/react-pages.md` (kit `Dialog` props).
- `release-notes.md`, `CHANGELOG.md` [0.7.1].
- `ui.d.ts`, copied to the CLI template and the demo.

## Part B (0.8.0): job history on the Queue page

**Today:**
- A finished job is deleted (`worker.rs` `Outcome::Done`), so there is no
  history.
- `jobs` has no start or finish time. Running jobs show `reservedUntil` as
  "next".
- No auto refresh. Rows show only `kind`.
- `jobs.created_at` is unindexed, though the list orders by it.

### B1. Data
- **Columns on `jobs`:**
  - `started_at instant null`: null for rows from before the upgrade; set at
    each claim;
  - `description str200 null`;
  - a `jobs_created_idx(created_at, id)` index.
- **New table `job_runs`:** `id uuid PK` (v7), its own id. One row per
  terminal outcome.
  - Columns:
    - `job_id uuid`;
    - `queue str64`, `kind str64`;
    - `description str200 null`;
    - `status str16`: `done`, `failed` or `cancelled`;
    - `attempts int`;
    - `created_at`, `started_at null`, `finished_at` (instants);
    - `duration_ms bigint null`;
    - `last_error str500 null`: the existing safe message;
    - `initiated_by bigint null`.
  - Indexes:
    - `job_runs_finished_idx(finished_at, id)`: the list, cursors and pruning;
    - `job_runs_job_idx(job_id, finished_at)`;
    - `job_runs_kind_idx(kind, finished_at, id)`.
  - Cursors and React keys use the history `id`. A job retried and finished
    again gets a new row, so retry cycles never collide.
- **Only a successful transition writes history, in its own transaction.**
  `settle`, `reap` and `cancel` become one transaction each:
  1. the conditional update or delete on the lease token or state, which must
     affect exactly one row;
  2. only then, the history insert;
  3. and the schedule-run update (C1).
  - Zero rows (a lost lease, taken over after an expired heartbeat) writes
    nothing.
- **Terminal outcomes:**
  - **`done`:** `Done`.
  - **`failed`:** the final retry, `Fail`, a permanent `Failure`, an invalid
    payload, an unknown kind's grace expired, or `reap` of an expired last
    attempt.
  - **`cancelled`:** `cancel` (`manage.rs`).
- **No row:**
  - intermediate retries;
  - `give_back`;
  - a temporary unknown kind;
  - `forget`. It removes the failed job, and its `failed` row stays. The
    "forget deletes the error for good" text (`en.ts`, `vi.ts`) is reworded.
- **Retention:** `[queue] history_retention_days` (default 7, 0 = no history,
  ≤ 3650). Pruned in `maintain` by `finished_at`, in keyed batches of 1,000,
  as `claim.rs` prunes slots.

### B2. `Job::describe`
- **Signature:** `fn describe(&self) -> Option<String> { None }`. Computed
  from the job at dispatch, stored in `jobs.description`, copied to
  `job_runs`.
- **Example:** `"deploy demo/web #12"`.
- **Shown to `queue.view` holders:** the docs say never to put secrets or
  personal data in it.
- **Checks:** at most 200 characters, cut on a character boundary; control
  characters removed; empty means none.
- **The payload is never sent to the panel.**

### B3. Admin API (`queue.view`)
- **`GET {admin}/api/queue/jobs`** gains `since` and `until` (RFC 3339, on
  `created_at`; `since > until` is a 422). Each `QueueJob` gains
  `description?` and `startedAt?`.
- **`GET {admin}/api/queue/history`**:
  - params `status=done|failed|cancelled`, `queue`, `kind`, `since`, `until`
    (on `finished_at`), `cursor` and `per_page` (≤ 100);
  - returns `{data: [JobRun], meta: {nextCursor?}}`, newest first;
  - unknown or repeated params are a 422.
- **`GET {admin}/api/queue/jobs/{id}`** returns `{job?: QueueJob, runs:
  [JobRun]}`: the runs by `job_id`, newest first, at most 20. It is a 404 when
  both are empty.
- **`QueueOverview`** gains done and failed counts over the last 24 h.
- **Routes:** listed in `http::routes`, with oracle cases (guest 401,
  member 403, token 401, admin 200, bad uuid 404).

### B4. Queue page
- **Tabs:** *Jobs* (pending, delayed, running, stalled, failed) and
  *History* (done, failed, cancelled).
- **Rows:** `description` under `kind`.
  - Running: started, plus elapsed.
  - Delayed: runs at.
  - History: finished, plus duration.
  - The kind is a button that opens the details dialog: timestamps,
    attempts, initiator, error, runs. Actions stay where they are today.
- **Filters:** status, queue, kind and a time range (1 h, 24 h, 7 days, or
  custom).
- **Auto refresh:**
  - Every 5 s while the tab is visible and no dialog is open, with an *Auto
    refresh* switch kept per browser (`localStorage`, try/catch).
  - It polls only while one page is loaded. After "load more" it pauses, with
    "Paused while browsing older rows · Back to latest"; *Back to latest*
    resets to page one. TanStack's infinite refetch, which fetches every
    loaded page, is not used for polling.
  - Rows are keyed by id; actions behave as today.
- **Naming:** *Scheduled* becomes **Delayed** ("Hẹn giờ"), with help: "a job
  dispatched to run later; recurring tasks are under System → Schedules".

### Test B
- **Rust** (`db_test!`, all three DBs):
  - **Outcomes and rows:**
    - `done` writes one row with timings;
    - retry then done gives two rows;
    - each failure path gives `failed`, `reap` included;
    - `cancel` gives `cancelled`;
    - intermediate retries, `give_back` and a temporary unknown kind write
      nothing.
  - **Ownership:** a lost lease, a takeover after an expired heartbeat, or a
    rollback writes nothing.
  - **Retention:** `history_retention_days = 0`; pruning.
  - **`describe`:** cut, stripped, empty means none.
  - **Routes:** filters, cursor, 422s, the detail 404, the oracle cases.
  - **Migrations:**
    - upgrade a database holding pending, running and failed jobs;
    - re-run after a partial DDL (MySQL commits per statement);
    - repeated rollback and re-apply.
- **Vitest:**
  - tabs, history rows, details from the keyboard;
  - auto refresh: paused while hidden, after "load more" and with a dialog
    open; Back to latest;
  - rows inserted or deleted at page boundaries;
  - Delayed and the reworded forget text;
  - the time range builds `since` and `until`.
- **E2E:** the demo dispatches a job; it shows running, then done in History,
  without a reload.

## Part C (0.8.0): System → Schedules

**Today:**
- Only `schedule:list` and `schedule:run` show schedules.
- `schedule_states` keeps `last_slot_at` and `active_job_id`, the overlap
  lock, behind a `FOR UPDATE` row lock. `schedule_slots` keeps claims.
- Outcomes are not stored; successful runs log at debug.
- `Overlapping` rolls the claim back.
- `Rule` and the `Schedule` fields are `pub(crate)`.

### C1. Data and core
- **New table `schedule_runs`:** `id uuid PK` (v7).
  - Columns:
    - `name str64`;
    - `slot_at instant null` (null for manual runs);
    - `trigger str16`: `schedule` or `manual`;
    - `started_at`, `finished_at null`;
    - `status str16`: `running`, `succeeded`, `failed`, `dispatched`,
      `skipped`, `cancelled` or `unknown`;
    - `job_id uuid null`;
    - `duration_ms bigint null`;
    - `error str500 null`;
    - `initiated_by bigint null`.
  - Indexes:
    - `schedule_runs_name_idx(name, started_at, id)`: lists and cursors;
    - `schedule_runs_started_idx(started_at, id)`: global pruning;
    - `schedule_runs_job_idx(job_id)`.
- **Job schedules:**
  - The claim transaction writes `dispatched` with `job_id`.
  - **The outcome is stored, never inferred.** The job's terminal transition
    (B1, same transaction) updates the run where `job_id = id` to
    `succeeded`, `failed` or `cancelled`, with `finished_at`, `duration_ms`
    and the safe error. This works with queue history disabled or pruned
    sooner.
  - A `dispatched` run whose job no longer exists reads **unknown**.
- **Closure schedules:**
  - The claim transaction writes `running`. The closure's result updates it
    to `succeeded` or `failed`; a panic writes `failed` ("panicked").
    Shutdown cancelling the task writes `unknown` ("interrupted by shutdown").
  - A crash leaves `running`. The page labels a `running` row older than the
    grace plus 1 hour **completion unknown**. There is no rule-period guess:
    cron has no fixed period.
  - **Errors:** `.run` closures return `AppResult<()>`, so their stored text is
    always "failed (see the logs)". `AppError` text is never persisted.
- **Reporting closures, new and additive:** `.task(|ctx: TaskCtx| async move
  { … })` returns `anyhow::Result<Option<String>>`, the same contract as a
  job's error.
  - **`Ok(Some(text))`** is a short summary of the run, for example "3
    databases backed up, 1.2 GB" or "2 certificates expire within 14 days".
  - **Errors:** a `queue::Failure` in the error chain stores its safe message.
    Any other error stores "failed (see the logs)".
  - **Limits:** summaries and messages are cut to 200 and 500 characters with
    control characters stripped. Both are shown to `schedules.view` holders,
    so the docs say never to include secrets.
  - **`TaskCtx`** is `{state, run_id, trigger, initiated_by}`. `run_id` is the
    `schedule_runs` id, a stable key for the app's own idempotency.
  - **Storage:** `schedule_runs` gains `summary str200 null`.
  - **Migration:** `.run` keeps working unchanged. Moving to `.task` is a
    one-line change: `|state|` becomes `|ctx|`, and `Ok(())` becomes
    `Ok(None)` or `Ok(Some(…))`.
- **Overlap:** a slot skipped by `without_overlapping` commits its slot row
  and a `skipped` run together, so no other instance runs it later.
  Ambiguous-commit reconciliation (`claim.rs`) rebuilds `Skipped` as well as
  `Mine(job_id)`. Missed slots stay log-only.
- **Retention:** `[schedule] history_retention_days` (default 7, 1–3650), by
  `started_at`. Pruned with the slots, in keyed batches.
- **Public read API** for the panel; nothing that changes a schedule:
  - `Schedules::all()` entries expose `name()`, `describe()`,
    `next_after(t)`, `action()` (`Job { kind }` or `Closure`) and
    `without_overlapping()`;
  - `schedule::states(db)` and `schedule::runs(db, name, cursor)`.
- **Run now, for job and closure schedules.**
  - **Job schedules:** dispatch the schedule's job.
  - **Closure schedules (`.run` and `.task`):** dispatch the internal job
    `rustcms.schedule.run {name, run_id}`. A worker runs the closure.
    - **At most once.** The internal kind has `max_attempts = 1` and the new
      `Job::AT_MOST_ONCE = true` (a const, default `false`, public). For such
      jobs, worker shutdown does not `give_back` (which would return the
      attempt). It settles the job `failed`, "interrupted by shutdown", and a
      crash is reaped as `failed`. Neither is ever run again.
    - **Timeout:** the schedule's `.timeout(d)`, a new builder (default 1 h,
      at most `[queue] max_timeout_secs`).
    - **Queue:** `default`, or `[schedule] queue` when set.
    - **Its terminal transition** updates the run row as for job schedules.
      For `.task`, the summary and the safe error are carried through the job
      outcome.
    - **The `rustcms.` prefix becomes reserved for job kinds:** application
      `Jobs::register` refuses it, and the internal kind registers through a
      core path. An unknown schedule name (removed since dispatch) fails the
      job permanently: "schedule not declared".
  - **`schedule::run_now(txn, state, name, actor)`** takes the caller's
    transaction, opened by the admin handler with `rbac::begin_as`. RBAC's
    `xact_lock` stays the first and only named lock, so there is no
    `rustcms_locks` seeding. In that transaction:
    1. ensure the `schedule_states` row (also with `schedule.enabled =
       false`);
    2. lock it `FOR UPDATE`, as `claim_in` does;
    3. refuse while another run of this schedule is unfinished: 409
       `write_conflict`, reason `running`.
       - **Job schedules with `without_overlapping`:** `active_job_id` is a
         live unfailed job, as today.
       - **Closure schedules, always:** a `running` or `dispatched` run row of
         the schedule, younger than its `.timeout` plus the grace. Automatic
         closure runs write that `running` row in their claim transaction,
         before executing, so a Run now during an automatic run is refused.
         Older rows count as finished (completion unknown);
    4. `dispatch_with(…, initiated_by = actor)`;
    5. set `active_job_id` for job schedules with `without_overlapping`;
    6. write the `manual` run (`dispatched`) and the audit entry
       `schedule.run`.
    - All of it commits together. `last_slot_at` is untouched.
  - **Races:** manual against manual, and manual against a slot, serialize on
    the state row. Automatic closure runs of adjacent slots may still overlap
    each other, as today: `without_overlapping` stays a job-schedule option,
    and this is documented.
  - **Without workers:** Run now still enqueues, and the page says no worker
    runs it, as the Queue page does.
  - **Bypasses, documented:** the console `schedule:run` (in process, now also
    writing a `manual` run) and a queue retry of a schedule's job skip the
    overlap check.

### C2. Admin API
- **Permissions:** `schedules.view` and `schedules.manage`, group
  `schedules`. `SystemLinks.schedules`.
- **`GET {admin}/api/schedules`** (`schedules.view`):
  - returns `{data: [ScheduleInfo], scheduler: {enabled, graceSecs},
    canManage}`;
  - `ScheduleInfo` is `{name, rule, action: {kind: "job", jobKind} | {kind:
    "closure"}, withoutOverlapping, nextAt?, lastSlotAt?, last?: ScheduleRun}`.
- **`GET {admin}/api/schedules/{name}/runs?cursor=&per_page=`**
  (`schedules.view`):
  - returns `{data: [ScheduleRun], meta}`;
  - `ScheduleRun` is `{id, slotAt?, trigger, startedAt, finishedAt?, status,
    durationMs?, error?, summary?, jobId?, initiatedBy?}`;
  - an unknown name is a 404.
- **`POST {admin}/api/schedules/{name}/run`** (`schedules.view` +
  `schedules.manage`):
  - permissions are checked before the name, then rechecked under the RBAC
    lock;
  - returns 202 `{run: ScheduleRun}`.
- **Routes:** in `http::routes`, with oracle cases for all three.

### C3. Schedules page
- **Navigation:** System → Schedules (icon `clock`), with help: "Recurring
  tasks declared by the app. Jobs waiting to run later are under Queue →
  Delayed."
- **The table:** one row per schedule.
  - name and rule ("every 5 min", "cron 0 3 * * *");
  - action (job kind or "task");
  - next run (relative and absolute);
  - last run: status, when, duration, error;
  - **Run now** for managers, with a confirm dialog;
  - the last run's summary, for `.task` schedules.
- **Run history:** the name is a button that opens the runs dialog (status,
  trigger, slot, start, duration, error, a link to the job in Queue).
- **Refresh:** the same auto refresh rule as the Queue page.
- **Scheduler off:** an alert when `schedule.enabled = false`.

### Test C
- **Rust** (`db_test!`):
  - **Closure runs:**
    - `.run`: `running`, then `succeeded`. An error, including one carrying a
      secret, stores the generic text only. A panic gives `failed`.
    - `.task`: the summary is stored, cut and stripped. A `Failure` in the
      chain stores its message; another error stores the generic text.
  - **Job runs:** `dispatched`, then `succeeded`, `failed` or `cancelled`
    from the job's transition, with queue history off. A missing job reads
    `unknown`.
  - **Overlap:** `skipped` is committed; reconciliation rebuilds it; no other
    instance runs the slot.
  - **Run now:**
    - manual/manual and manual/slot races;
    - the 409;
    - the audit entry is in the same transaction;
    - the initiator reaches the job;
    - `last_slot_at` is unchanged;
    - it works with the scheduler disabled;
    - closure Run now:
      - the internal job runs once and is never retried;
      - a crash mid-run is reaped as `failed`;
      - **shutdown mid-run settles it `failed` with no second invocation**,
        tested through an effect counter across a worker restart;
      - the timeout is honoured;
      - an undeclared name fails permanently;
      - `rustcms.` kinds are refused for apps.
    - Run now while an automatic closure run is in progress is refused (409);
      after its timeout plus grace it is allowed.
  - **Pruning; routes** (404, 403 before 404, oracle); **migrations** as in B.
- **Vitest:**
  - the table, next and last run;
  - the runs dialog from the keyboard;
  - Run now with confirm, hidden without manage;
  - the summary column;
  - "completion unknown";
  - the scheduler-off alert and the help text.
- **E2E:** the demo has one job schedule and one `.task` schedule. Run now
  on each shows the run dispatched, then succeeded with its summary, without
  a reload.
