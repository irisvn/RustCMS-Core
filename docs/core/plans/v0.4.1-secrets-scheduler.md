# v0.4.1 plan: encrypted columns (W8), then the scheduler (W4)

> Historical: both shipped in 0.4.1 (tag 2026-10-18; ADR 0030, ADR 0031).
> The CHANGELOG and the ADRs describe what was built.

Requested by RDockPanel on 2026-10-18 and ordered by the maintainer:
- W8 first. It blocks RDockPanel's M5: service environment variables and
  registry credentials.
- W4 second: reconcile every ~60 s, periodic `docker prune`.
- W5 (React SDK) and TOTP come later.

This file starts with W8. W4 gets its own section after W8 ships.

## W8: encrypted columns (plan round 3, 2026-10-18; Codex rounds 1–2 applied)

### Goals and non-goals
- Goals:
  - Apps store secrets (one string, or a map of named secrets) in their own
    tables, encrypted with `APP_KEY`.
  - Secrets are never sent to the browser, never logged, and never kept in
    the audit log.
  - `APP_KEY` can rotate without losing them.
  - Admin resources edit them write-only.
- Non-goals:
  - Searching, sorting or filtering on encrypted values.
  - Encrypting whole tables.
  - KMS keys.
  - Zeroizing plaintext in memory.
  - CSV import of encrypted fields (exports never include them).
- **Trusted escape hatches**, stated in the guide: raw SQL, and app code that
  calls `open`.

### Keys (rustcms-core, `crypto` module)
- **`Keyring { current, previous }`:**
  - The current key is `app.key` (`APP_KEY`).
  - The previous keys are `app.previous_keys`: a TOML array in files; in the
    environment, `APP_PREVIOUS_KEYS` as a comma-separated list of `base64:`
    keys, with `APP_PREVIOUS_KEYS_FILE` read by the existing `_FILE` rules.
  - Boot fails, without quoting a key, on:
    - a bad key;
    - a duplicate;
    - a previous key equal to the current one;
    - two key ids that collide.
- **Key id:** the first 8 bytes, in hex, of `key.derive("rustcms/key-id/v1")`.
  It is deterministic, so rows sealed with the same key are linkable (stated
  in the ADR).
- **Wiring:**
  - `AppState::keyring()`.
  - `Ctx::keyring()`, for hooks and actions; the engine's `Ctx` gets it from
    the state.
  - Jobs and console commands reach it through the state.
  - `TestApp` sets it from its config.
  - Every settings read takes the keyring: `settings::read`, `load` and
    `get`.
- **Previous keys only decrypt.** Sessions, JWTs, refresh tokens and
  reset/invitation links keep using the current key only. Tests prove that a
  previous key authenticates none of them.
- **Encryption key:** `key.derive("rustcms/encrypted/v1")`. Settings keep
  their own purpose.

### Format
- Envelope: `rcms1.<kid>.<payload>`:
  - `kid` is 16 lowercase hex characters;
  - `payload` is base64url without padding of `nonce (12) ‖ ciphertext ‖ tag
    (16)`;
  - parsing is strict: the exact prefix and kid length, no padding,
    canonical base64.
- Envelopes are at most 60 000 bytes (checked before decoding), and the
  plaintext (the JSON of `T`) at most 32 KiB. A sealed envelope then always
  fits a MySQL `TEXT` column (65 535 bytes) and the other `Text` types.
- **AAD:** a canonical, length-prefixed tuple, each part a u32 length and its
  bytes:
  1. the domain, `rustcms/encrypted/v1`;
  2. the header, `rcms1.<kid>`;
  3. the table (with its schema, if any);
  4. the column;
  5. a row tag: `0` for none, or `1` followed by the row identity, which is
     the primary key's canonical text (an integer in decimal, a UUID
     lowercase).

  There is no ambiguity: an absent row differs from `"-"`, and parts may
  contain `/`.
- AES-256-GCM with a random 96-bit nonce. The nonce limit (2³² seals per key)
  is far beyond any panel; rotating resets it. Stated in the ADR.
- **One failure:** `Unreadable`, a single opaque kind. A wrong key, an
  altered ciphertext, the wrong context and a malformed envelope all look
  alike, by design.
- **Errors never quote values:** sealing and opening return static errors,
  and serde errors are dropped as `settings.rs` already does.

### `Encrypted<T>` in models
- It is a SeaORM value type around the envelope string. A compile fixture
  covers required and `Option<Encrypted<T>>` fields: `From<Encrypted<T>> for
  sea_orm::Value`, `TryGetable`, `ValueType`, `Nullable`.
- A damaged envelope is loaded as it is, so `open()` fails; loading never
  fails because of it.
- `seal(&keyring, &context, &value)`, `open(&keyring, &context) -> Result<T,
  Unreadable>`, `key_id()` (an unauthenticated hint), and
  `is_current(&keyring, &context)` (true only when the envelope opens with
  the current key in that context).
- `Context::column(table, column)` and `.row(identity)`.
- `Debug` prints `Encrypted(<kid>)`. `Serialize` writes `null`.
  `Deserialize` always fails, so `ActiveModel::from_json` cannot be used on
  models with encrypted columns (stated in the guide).
- Map keys and ciphertext length are visible to whoever can read the row:
  stated in the ADR.

### Rotation: `key:reencrypt [--dry-run] [--batch 500]`
- **Registered columns:**
  - `AppBuilder::encrypted_column::<E>(column, rule)` registers a column; the
    admin `Field::encrypted*` registers its own.
  - The primary key must be a single column; a composite one panics at
    registration.
  - `rustcms key:reencrypt --list` prints the inventory of columns and
    settings groups.
- **For each column:**
  - It walks rows by keyset pagination on the primary key, in short
    transactions of one batch each, and skips SQL NULL.
  - It **opens every envelope**, even one already under the current key.
    Only a current-key envelope that opens counts as done; an envelope that
    claims the current key but fails counts as unreadable.
  - Others are sealed again with the current key and the same context, then
    written with a compare-and-swap: `UPDATE … SET col = new WHERE pk = ? AND
    col = old`. The comparison is bytewise: `BINARY` on MySQL, so a column
    collation cannot make two envelopes equal.
  - A row that changed in between is counted as changed and left alone.
  - `--dry-run` opens and counts, and writes nothing.
  - Unreadable rows are listed by table, column and primary key, and never
    modified.
- **Settings:** a new `settings::reseal(txn, keyring, group)`.
  - Under `db::begin_write` (SQLite `BEGIN IMMEDIATE`) and the group's row
    lock, it reads the raw row.
  - Each secret is first tried with the current key. One that opens is kept
    byte for byte; only a secret that opens with a previous key is sealed
    again with the current key, at the same version.
  - Nothing to reseal means no `UPDATE`, so a second run changes nothing.
  - Only the `secrets` column is updated. The version, the values, the
    attribution, unknown fields and unreadable entries are preserved.
- **Exit status:** 0 only when nothing is unreadable, changed or left.
  - Concurrent runs are safe thanks to the CAS, but their counts are
    approximate. The guide says to run it once more until it reports 0.
- **Procedure** (`operations/app-key.md`):
  1. Put the new key in `APP_KEY` and the old one in `APP_PREVIOUS_KEYS`.
  2. Restart **every** process, so no old-key writer is left. Stop them
     all, then start them, rather than a rolling restart: a process still on
     the old key cannot read what the new ones seal.
  3. Run `key:reencrypt` until it reports 0.
  4. Remove the previous key, restart, and run `key:reencrypt --dry-run`:
     it must report 0 unreadable.

### Admin resources
- **Declarations:**
  - `Field::encrypted()` is one secret string, `Encrypted<String>`.
  - `Field::encrypted_map()` is named secrets,
    `Encrypted<BTreeMap<String, String>>`, with KeyValue-style bounds:
    `max_items`, key and value lengths.
  - Both use String or Text columns.
  - Both register the column for `key:reencrypt`, with the context table and
    column (no row; see the ADR for the swap consequence).
- **Read contract.** `record()` holds a private secret view; the wire gets
  only this:
  - A string: `{"state": "set" | "unset" | "unreadable"}`.
  - A map:
    - `{"state": "set", "keys": [..], "revision": "<r>"}`;
    - `{"state": "unset"}`;
    - `{"state": "unreadable", "revision": "<r>"}`.
  - The keys come only from opening the map, so an unreadable map shows none.
  - `revision` is `HMAC(derive("rustcms/encrypted-revision/v1"), envelope)`,
    truncated to 8 bytes. It does not reveal the content and changes with
    every write.
  - Key names follow the field's `readable` rule: without it, only `state`
    and `revision` are sent. A writer may get a revision without the names.
  - An unset map (SQL NULL) has the fixed revision `"none"`.
  - Policies, titles, hooks, exports, dashboards and custom pages never see
    plaintext or envelopes.
- **Write contract.** A dedicated validator, not the KeyValue one.
  - A string:
    - the field left out: unchanged;
    - `{"replace": "<v>"}`: replaced;
    - `{"clear": true}`: cleared, only when nullable and not required.
  - A map: `{"revision": "<r>"?, "set": {"K": "v", ..}, "keep": ["K", ..]}`.
    - The result is `set` plus the kept keys; any other key is removed.
    - **Every change to an existing record's map needs the current
      `revision`**: keeping, removing, replacing everything, or clearing.
      Otherwise the answer is 409: the form is stale, and keys added in
      between are never lost. On create, `revision` is absent.
    - `keep` on create, or a key both kept and set, is 422.
    - Renaming a key means removing it and setting the new one.
    - `{"revision": "<r>", "clear": true}` clears the map when the column is
      nullable.
  - **Resolution:** inside the write transaction, on the freshly locked model,
    after the `mutate_before_*` hooks:
    1. check the revision;
    2. open the stored map, **only when `keep` is not empty**: replacing
       everything and clearing never decrypt, so they work on an unreadable
       map;
    3. merge;
    4. validate the bounds on the complete map;
    5. seal.
  - Keeping a key of an unreadable map is 422 `unreadable`. Replacing
    everything (no `keep`, the right revision) recovers it.
  - Hooks see the submitted operations, never the stored values.
- **Audit:** the diff compares the stored envelopes privately and records
  `[redacted] → [redacted]` when they differ. Envelopes and plaintext are
  never persisted. `audit_redact` is forced on.
- **Exposure paths closed at boot.** An encrypted field cannot be:
  - `sortable`, `searchable` or `filterable`;
  - the title or a `belongs_to`;
  - in a table column, a filter or a dashboard selection;
  - in the import or export columns (excluded from the generated ones, a
    panic if listed by hand);
  - a primary or relation key;
  - given a column default.

  `auto_columns`, `import_fields` and `export_columns` skip encrypted fields.
- **Idempotency:** stored responses keep their current shape (CRUD receipts
  store keys, action receipts store key outcomes), so no secret view is
  replayed.
- **SPA:**
  - `encrypted()` uses `SecretWidget` (Keep, Replace, Clear), driven by
    `state`.
  - `encrypted_map()` is a new `SecretMap` widget:
    - stored keys show "kept" with Replace and Remove;
    - new rows take a key and a value;
    - values are never prefilled;
    - it sends the operations with the revision;
    - on 409 it offers to reload.
  - The form protection and conversion code accepts these shapes.
  - Contract: a new input type `secret_map`, the props, `VOCABULARY_VERSION`
    + 1, `UPDATE_CONTRACT` / `UPDATE_TYPES`.

### Test
- **Core:**

  - each tampered part fails: kid, nonce, ciphertext, tag, padding,

    - the wrong table, column or row;

- **Vitest:** `SecretMap` (never prefilled, its operations, the revision, 409

- **E2E (Chrome):**

## W4: scheduler (plan round 3, 2026-10-18; Codex rounds 1–2 applied)

RDockPanel asks for reconcile/drift every ~60 s and a periodic `docker
prune`, run only in `serve`, never in console commands or tests. This
supersedes the 0.4.0 draft's "ticks never overlap" promise: overlap is
governed by the rules below.

### Today
- Periodic work is ad-hoc `tokio::spawn` loops in providers' `boot`, under
  `jobs::exclusive`. They also start in console commands and `TestApp`, and
  without Redis every instance runs them.
- They stay as they are in 0.4.1. Moving them is a follow-up, and the guide
  says so.

### Declaring
```rust
app.schedule(Schedule::every("reconcile", Duration::from_secs(60)).job(|| Reconcile {}).without_overlapping());
app.schedule(Schedule::cron("docker-prune", "0 3 * * *")?.job(|| Prune { until: "24h".into() }));
app.schedule(Schedule::every("warm-cache", Duration::from_secs(300)).run(|state| async move { warm(&state).await }));
```
- **Names:** `[a-z0-9_.-]{1,64}`, unique; a duplicate panics. Names starting
  with `rustcms.` are reserved.
- **`every(d)`:** 10 s ≤ d ≤ 7 days, whole seconds.
- **`cron(expr)`:**
  - five fields, UTC only (no time zones, no DST);
  - parsed with `croner` 4.0.x, whose license (MIT), MSRV (≤ our 1.94) and
    release age (at least 2 weeks) are checked when it is added;
  - day-of-month and day-of-week combine with OR, as in Vixie cron;
  - no seconds, no year, no extensions;
  - an expression with no fire time in the next 5 years (`30 2 30 2 *`) is
    an `Err`.
- **Actions:**
  - `.job(make)` enqueues a queue `Job` per slot. It registers `J` with the
    queue if not registered yet. Registering again is idempotent only for the
    same concrete type (`TypeId`); two types sharing a `KIND` fail
    registration, in either order. It needs
    workers serving `J`'s queue (`serve`, or `queue:work`). This is the
    durable form: retries and leases come from the queue (successful jobs are
    deleted, as today).
  - `.run(f)` runs in the process: `f: Fn(AppState) -> Future<Output =
    AppResult<()>>`. Best effort: at most one invocation per claimed slot. A
    crash between the claim and the call, or during the call, loses or
    truncates that run.
- **`.without_overlapping()` (on `.job`):** an admission control on automatic
  enqueues. A slot is skipped (and logged) while the schedule's active job
  (`schedule_states.active_job_id`, see the claim protocol) still exists in the
  queue and has not failed for good. It is kept apart from claim retention,
  so a job pending past the 7-day pruning still blocks. Manual runs
  (`schedule:run`) and `queue:retry` of an older failed job are not admitted
  through it, and can overlap (stated). The queue's lease, renewed by the worker, is the
  execution lock. If a worker dies, its lease expires, and the job is retried
  or fails; the schedule resumes after either. This is the supported recipe
  for Docker reconciliation, which must also be idempotent (a retried job may
  repeat part of its work).

### Slots and time
- A slot is a whole-second UTC instant shared by every instance:
  - `every(d)`: the multiples of `d` since the Unix epoch;
  - `cron`: its fire times.
- **Clock assumption:** instances' clocks agree within 1 s (NTP).
  - Skew can make an instance claim a slot up to the skew early, or late.
  - The database claim prevents a second run of the same slot; it cannot
    stop a fast clock from starting a slot early. This is stated in the
    guide.
- **Eligibility:** a slot is eligible from its instant until
  `instant + schedule.grace_secs` (default 30).
  - **At start:** the next slot strictly after now.
  - **While waiting:** sleep in chunks of at most 60 s, recomputing from wall
    time on every wake. Long cron sleeps and clock jumps are thus noticed.
  - **On waking:** the latest elapsed slot runs if still within grace; older
    elapsed slots are skipped, never replayed.
  - **Clock jumps:** jumping backwards recomputes the next slot (claims stop
    re-runs of slots already claimed); jumping forwards skips what is beyond
    grace.
  - **Rechecked after the claim insert, before commit:** a claim whose wait
    (lock contention) crossed the grace is rolled back and the slot skipped.

### Claim protocol
- A table `schedule_states (name PK, active_job_id, last_slot_at,
  updated_at)`: one row per schedule, inserted if missing when the scheduler
  starts, and never pruned.
- A table `schedule_slots`:
  - columns: `name` (64), `slot_at` (instant, whole seconds), `claimed_at`,
    `instance` (64), `job_id` (nullable);
  - primary key `(name, slot_at)`; index on `claimed_at`;
  - a framework migration through the `create_table` helpers, re-runnable on
    MySQL.
- Each claim runs in `db::begin_write`: `BEGIN IMMEDIATE` on SQLite, `READ
  COMMITTED` on MySQL, a write transaction on PostgreSQL. A timeout of 5 s
  bounds it.
  0. **Lock the schedule's state row** (`SELECT … FOR UPDATE`; SQLite's
     `BEGIN IMMEDIATE` already serializes writers). Claims of one schedule,
     adjacent slots included, are thus serialized across instances.
  1. **Insert the claim.** The unique key arbitrates, and there is no
     existence check first.
     - PostgreSQL/SQLite: `INSERT … ON CONFLICT (name, slot_at) DO NOTHING`;
       success is decided by the affected rows.
     - MySQL: a plain `INSERT`; error 1062 (duplicate) means "not ours"
       (MySQL keeps the transaction usable after it). No `INSERT IGNORE`,
       which hides other errors. Every field is validated and bounded first.
  2. **Recheck the grace** (above).
  3. **`.without_overlapping()`:** under the state lock, look up
     `active_job_id` in the queue; while that job is pending or running, roll
     back and skip.
  4. **`.job`:** `queue::dispatch` in the same transaction, and record its id
     in the claim and as the state row's `active_job_id` (with
     `last_slot_at`).
  5. **Commit.** No external work runs inside the transaction.
- **Guarantee:** at most one committed enqueue (or `.run` invocation) per
  slot while its claim row is kept. The queue still runs jobs at least once.
- **Failures:**
  - a crash before commit rolls everything back;
  - a crash after commit leaves the job, which is durable;
  - a transient database error (409-class, a timeout) is retried with the
    same slot key, at most until the grace ends;
  - an ambiguous commit (the connection lost during commit) is resolved by
    reading the claim row before retrying.

### Overlap
- `.job` without `without_overlapping`: slots enqueue independently, and
  workers may run them concurrently.
- `.run`, on one instance: never concurrent. A slot that comes while the
  previous run is in progress is skipped (a completion guard clears the flag,
  also on panic).
- `.run`, across instances: two long runs can overlap. The guide says so and
  points to `.job` + `without_overlapping`.

### Supervision and shutdown
- The scheduler runs **only in `App::serve_on`**. An owner value holds it
  there: its `Drop` explicitly cancels the scheduler and **aborts** the
  scheduler's own `JoinSet`, which holds every claim task and `.run` action
  (dropping a handle would detach a task). A server error or a dropped
  `serve_on` future therefore stops everything. Normal shutdown joins them
  within the bounds below.
  - Console commands, `queue:work` and `TestApp` never start it.
  - `[schedule] enabled = false` turns it off.
- It never awaits an action or a claim inline:
  - each due schedule's claim runs as its own task, at most one in flight
    per schedule, each bounded (5 s plus retries within grace). A blocked
    claim never consumes another schedule's grace.
  - pruning runs as its own task too;
  - `.run` closures run in the scheduler's `JoinSet` with a completion
    guard; a panic is caught and logged.
- On the stop signal it admits no new claim. A claim already committing
  finishes. Running `.run` closures get `[realtime] shutdown_grace_secs`
  (the same grace as `Shutdown`), then the set is aborted.

### Pruning
- Claims whose `claimed_at` is older than 7 days are deleted:
  - hourly, by the scheduler's own internal step (not a user schedule);
  - in batches of 1,000 by key;
  - a failure is logged and retried at the next hour.
- Seven days is far beyond grace plus skew, so a slot is never replayed
  because its claim was pruned.
- **Capacity:** a 10 s schedule keeps about 60,500 rows, a 60 s one about
  10,000. After a disabled period nothing is replayed (slots are not caught
  up).

### Commands
- `schedule:list`: name, rule, action kind, overlap policy, next slot, and
  the last claimed slot with its job id.
- `schedule:run <name>`: a manual run now.
  - It is not a slot: no claim, no grace, no `without_overlapping`, and it
    ignores `enabled`. It can therefore overlap automatic and manual runs
    (stated).
  - `.job` enqueues one and prints its id (workers run it).
  - `.run` runs it in the command, exiting 1 when it returns `Err`. Ctrl-C
    cancels it (the future is dropped) and the command exits non-zero.

### Config `[schedule]`
- `enabled = true`
- `grace_secs = 30` (1 to 300)

### Test
- **Unit (an injected `Clock`; tokio's paused time for sleeps, since paused
  time does not move `Utc::now`):**
  - `every` alignment;
  - the next slot after any instant;
  - cron:
    - UTC fire times;
    - month boundaries, Feb 29;
    - DOM/DOW OR;
    - an impossible expression;
  - eligibility:
    - at start;
    - after a pause;
    - within and beyond grace;
    - clock jumps both ways.
  - bounds on `every`, names, the reserved prefix.
- **`db_test!` (each backend required in the matrix):**
  - two apps on one database, with separate connections and a barrier, race
    for one slot:
    - one claim and one job;
    - the loser does nothing;
    - when the winner rolls back, the next attempt can claim.
  - a claim and its dispatch roll back together;
  - a lock wait that crosses the grace skips the slot;
  - a transient error is retried within the grace; an ambiguous commit is
    resolved from the claim row;
  - `without_overlapping`:
    - skipped while the active job is pending or running;
    - resumes after it succeeds or fails for good;
    - adjacent-slot claims racing on separate connections admit one job;
    - a job still pending after its claim was pruned still blocks;
    - a `queue:retry` of an older failed job is not admission-controlled
      (it may overlap, as documented);
  - registration: the same job type through `.job` and `app.job` is fine; two
    types sharing a `KIND` fail, in either order;
  - a blocked database claim on one schedule leaves a healthy schedule on
    time;
  - `.run`:
    - skipped while running;
    - a panicking or slow schedule does not stop the others;
  - pruning:
    - removes rows older than 7 days, in batches;
    - keeps newer rows.
- **Lifecycle:**
  - `serve_on` starts the scheduler, and the stop signal stops claims;
  - shutdown with a `.run` in progress (the grace, then abort);
  - a server error, and a dropped `serve_on` future, with a `.run` in
    progress: the action is aborted and nothing is left running;
  - `TestApp` and console commands never start it;
  - `enabled = false`.
- **Commands:**
  - `schedule:list`;
  - `schedule:run`:
    - enqueues without a claim, and prints the job id;
    - a failing `.run` exits 1.
