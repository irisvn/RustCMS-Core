# ADR 0028: A process-local hub for live data

- Status: accepted (0.4, W3)
- Date: 2026-10-17

## Context

Several viewers of the same live data (a container's stats) should share one
producer, not each poll the source. The producer should stop when nobody
watches, and a slow viewer should not hold everyone back.

## Decision

- `rustcms_core::realtime::Hub<K>` maps keys to producers.
  - `subscribe(key, make)` starts `make()` (a `Stream<Item = Event>`) for the
    first subscriber; later subscribers share it.
  - `publish(key, event)` sends to current subscribers and never creates a
    key.
- The hub carries `Event`s that are already serialized and at most 64 KiB
  each, so its memory is bounded before anything enters it. That is 64
  events per key and `max_keys` (1000) keys; beyond that, `HubFull`.
- **Lifecycle:**
  - subscribe and unsubscribe are atomic under one lock;
  - the last unsubscribe arms an idle timer (`idle_grace`, 5 s), which stops
    the producer only if nobody came back meanwhile. A stale timer is
    ignored, because each entry has an id and an activity counter.
  - A stopping producer is awaited before the key's next one starts, and it
    counts against `max_keys` meanwhile.
  - A producer that ends or panics gives its subscribers `Ended`, and the
    next subscribe starts afresh.
  - Producers stop with `Shutdown`.
- A subscriber that falls behind gets `Lagged(n)`. As server-sent events
  (`Subscription::into_events`) that becomes `event: resync`, so the page
  reloads its state.
- The hub knows no users. A key holds only what decides the data
  (`container:<id>`), data that differs by user never shares a key, and
  access is checked by the route and the stream's target check.

## Consequences

- The hub is per process: each instance runs its own producers. There is no
  cross-instance fan-out in 0.4.
- Applications get stream helpers and timers from `rustcms::realtime`
  (`stream`, `StreamExt`, `time`), so producers need no crate of their own.
